SUMMARY

Financial sovereignty, built on local privacy.

Rotki is a privacy-first portfolio tracker, analytics, and accounting tool designed to protect user sovereignty.

It empowers users to monitor assets across multiple blockchains and DeFi protocols while keeping all sensitive data securely stored on their local machine.

THE BRIEF
PROJECT GOALS

Simplify multi-chain accounting: Translate complex on-chain data into clean, actionable financial metrics.

Scalable local UI: Design a local-first interface capable of handling thousands of historical transactions without causing cognitive overload.

PROBLEM

Fragmented UX and privacy leaks. Crypto users manage assets across multiple chains, but mainstream trackers store sensitive transaction data on centralized servers.

Conversely, existing local-first alternatives often suffer from cluttered, developer-centric interfaces due to technical constraints.

02 RESEARCH & INSIGHTS

Research revealed high friction, fragmented transaction histories across chains, and significant privacy anxieties regarding cloud-based tracking.

64% Users worry about centralization and third-party leaks of their financial records.
41% DeFi transactions require manual cost-basis adjustments in spreadsheets due to bad data.
18% Tax reporting mistakes occurred due to poor chain parsing and missing gas fee calculations.
03 PERSONAS & USER NEEDS

Two primary user groups were identified, each with very different expectations.

PRIVACY ADVOCATE

Age: 25-40 Role: DeFi Power User / Self-custody investor.

Frustrations

  • Centralized servers linking IP addresses and wallets to real identity.
  • Cluttered protocol dashboards that hide net worth.

Needs

  • Hardened local cryptography and privacy defaults.
  • Clean, customizable dashboard layout.

Goals

Track balances across multiple EVM and non-EVM chains without giving up custody or data ownership.

ACCOUNTANT / AUDITOR

Age: 30-55 Role: Tax Specialist or portfolio auditor.

Frustrations

  • Messy CSV data exports with gaps.
  • Handling multiple fiat valuation rules.

Needs

  • Double-entry ledger precision.
  • Custom tax accounting rules (FIFO, LIFO).

Goals

Generate verified, audit-proof reports that match blockchain histories perfectly with zero metadata leaks.

STRUCTURAL TENSION

The core tension wasn’t usability. It was local privacy vs. real-time UX.

Local Storage needed:

  • Encryption keys
  • Local sync cycles
  • Heavy client parsing
  • Manual node connection

Real-time tracker wanted:

  • Instant valuations
  • Zero setup friction
  • Cross-device sync
  • Automatic pricing updates

This created friction:

The more privacy safeguards and local encryption applied, the slower the initial sync and indexing times. Redesigning this balance required progressive data disclosure and background RPC syncing.

The challenge wasn’t just skinning a dashboard. It was explaining local-first data states so users understand their assets are secure.

04 USER FLOWS & IA

Key flows were designed to index multi-chain data and export compliant bookkeeping reports.

If something can be misunderstood, it eventually will.

01 Sync address history

User Privacy Advocate
Problem Connecting nodes directly leaked IP metadata or failed due to heavy sync times.
Design approach Progressive sync indicators with custom RPC input nodes and background indexing.
Outcome
↓ IP exposure risk
↑ Sync success rate

02 Label transactions

User Privacy Advocate
Problem Manual categorization of DeFi transactions was slow and confusing.
Design approach Inline tagging, auto-detecting gas fees, and customizable batch classification rules.
Outcome
↑ User speed
↓ Spreadsheet usage

03 Export tax reports

User Accountant
Problem Audits failed because cost-basis calculations didn't account for complex DeFi loops.
Design approach FIFO/LIFO selectors with instant validation checking for missing historical valuation data.
Outcome
↓ Failed export reports
↓ Audit prep time

04 Track DeFi pools

User Privacy Advocate
Problem Liquidity pool state was hard to parse without centralized indexers.
Design approach Aggregate protocol balances directly from chain queries under a unified asset view.
Outcome
↑ Dashboard accuracy
↓ API dependencies

Flows were simplified to reduce steps, ambiguity and processing bottlenecks.

These flows were validated against the full user journey to ensure consistency across protocols.

WHAT WAS DIFFICULT?
01

On whether to support auto-syncing profiles via cloud backups. The developers wanted convenience. We pushed to keep profiles fully local and encrypted on disk, using decentralized p2p channels only when explicitly activated.

02

On transaction filtering. Some contributors wanted exhaustive table views. We argued for progressive disclosure, letting users hide small-dust balances to reduce visual noise.

A CONTROVERSIAL DECISION

We intentionally hid small-balance 'dust' tokens and minor gas refunds by default. This cleaned up the dashboard significantly, but raised concerns about auditing transparency. Instead of adding complex setup screens, we introduced:

– One-click 'Show Dust' toggle – Automatic dust grouping – Contextual filtering rules
THE RESULT

Cleaner dashboards, reliable ledger states, audit-ready reports.
