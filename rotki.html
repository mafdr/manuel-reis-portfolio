SUMMARY

Designing trust before ask.

Rotki is a privacy-first crypto portfolio tracker. The product's promise is that your financial data stays on your device, always.

But the onboarding flow asks users to configure API keys for third-party services before showing them anything of value — undermining the very trust it needs to earn.

CLIENT Rotki (Open Source)
YEAR 2026
ROLE UX Designer (Onboarding)
SCOPE First-run experience
COMPANY SIZE Global open-source community.
INDUSTRY Web3 / Crypto portfolio management.
CONSTRAINT Open-source, no tracking, local data.
PROJECT TYPE Onboarding redesign.
TIMELINE 3 months from discovery to rollout.
THE BRIEF
PROJECT GOALS

Move from setup-first to value-first: show what the product does before asking anything from the user.

Sequence configuration progressively — when it's relevant — not as a prerequisite to seeing anything.

PROBLEM

The existing onboarding asks users to trust the product in exactly the wrong order. By step 3, before seeing a single meaningful screen, users are directed to create an Etherscan account, generate API keys, and configure RPC nodes.

The user who cares most about financial privacy — Rotki's core audience — is precisely the user who stops here.

01 DISCOVERY

Discovery focused on understanding how privacy-conscious crypto investors experience onboarding — and where trust breaks down before they see any value.

UX RESEARCH METHODS

The goal was identifying real friction points in the first-run experience.

Community surveys  ·  User interviews  ·  Persona profiles  ·  Onboarding audit  ·  Competitor analysis

02 RESEARCH & INSIGHTS

Research revealed that Rotki's core audience — privacy-conscious crypto investors — drops off precisely at the moments the product asks for the most trust, before earning any.

64% Users worry about centralization and third-party leaks of their financial records.
41% Abandoned onboarding at the Etherscan API key step — before seeing any value.
6 Steps required before seeing a dashboard. Most users dropped off by step 3.
03 PERSONAS & USER NEEDS

Two primary user groups were identified, each with very different expectations.

PRIVACY ADVOCATE

Age: 25-40 Role: DeFi Power User / Self-custody investor.

Frustrations

  • Centralized servers linking IP addresses and wallets to real identity.
  • Being asked to configure third-party API keys before seeing anything useful.

Needs

  • Understand what the product does — and what it doesn't — before committing.
  • See real value immediately after connecting a wallet.

Goals

Track balances across multiple chains without giving up custody or data ownership.

ACCOUNTANT / AUDITOR

Age: 30-55 Role: Tax Specialist or portfolio auditor.

Frustrations

  • Technical setup requirements that assume developer knowledge.
  • Messy CSV exports with gaps and missing cost-basis data.

Needs

  • Double-entry ledger precision.
  • Custom tax accounting rules (FIFO, LIFO).

Goals

Generate verified, audit-proof reports that match blockchain histories perfectly with zero metadata leaks.

STRUCTURAL TENSION

The core tension wasn't usability. It was earning trust before asking for effort.

What the product needed:

  • Local encryption keys
  • Third-party API setup
  • RPC node configuration
  • Wallet address input

What the user wanted:

  • See value immediately
  • Zero setup friction
  • Understand the privacy promise
  • Feel in control from step one

This created friction:

The more configuration required upfront, the higher the drop-off before any value was seen. The redesign resolves this by sequencing configuration progressively — after the user has a reason to stay.

The user who cares most about financial privacy is precisely the user who stops when asked to trust before being shown why.

04 USER FLOWS & IA

The core shift: move from setup-first to value-first. Configuration happens progressively, when it's relevant.

If something can be misunderstood, it eventually will.

Before — setup first

Step 1 Download & install — security warnings before even opening.
Step 2 Create local account — no context on why it exists or what it protects.
Step 3 Configure Etherscan API key — leave the app, create a third-party account, copy key. Before seeing any value.
Step 4–6 Configure RPC nodes, add wallets, add exchange keys.
Outcome
↓ Most users dropped off by step 3

After — value first

Step 1 See the promise — show what the product does with a visual, before asking anything.
Step 2 Create local account — with clear context: "this password encrypts your data locally, not on any server."
Step 3 Add one wallet — minimum viable connection, see your first balance immediately.
Step 4 Live dashboard — user has seen real value. Now earn the right to ask for more.
Outcome
↑ Activation rate
↓ Drop-off at configuration steps

Decision 1 — show the product first

Problem The first screen was a login form with a warning: "Do not forget your password. It cannot be recovered." That's the opening move.
Design approach Replace the login screen with a demo preview of the dashboard. One line of copy: "Your financial data. Only on your device. Always." The form comes second.
Outcome
↑ Users reaching account creation
↓ Immediate drop-off at first screen

Decision 2 — reframe the password step

Problem Local encryption is Rotki's strongest differentiator. The current screen treats it as a risk disclaimer rather than a selling point.
Design approach Reframe: "this password is the key to your private vault — rotki uses it to encrypt your database, which lives only on this machine." Show what doesn't happen: "Never sent to any server."
Outcome
↑ Trust perception at account creation
WHAT WAS DIFFICULT?
01

Working with a product that's technically complex by nature. Rotki does require configuration — the redesign doesn't remove that complexity, it sequences it differently. The goal wasn't to dumb it down but to earn trust before asking for effort.

02

The install step. macOS and Windows security warnings before the app even opens are real friction points — largely outside the product's control. A better "what to expect when you install" moment in the download flow could help, but was scoped out of this work.

A CONTROVERSIAL DECISION

We removed Etherscan setup from the critical path entirely. This is technically correct — without it, queries are slower — but it's the wrong trade-off for first-time users. After adding their first wallet, users see their portfolio immediately, with a non-blocking nudge:

– "Add a free Etherscan key to make balance queries faster" – Shown contextually, not as a prerequisite – Critical path = shortest path to value
THE RESULT

Fewer steps. Clearer promise. More users reaching the dashboard.

Less friction. Clearer promise. More financial sovereignty.

07 TAKEAWAYS

Designing for trust means sequencing correctly. The product doesn't need to be simpler — it needs to earn attention before asking for effort.

The rest of the product — dashboard, tax reporting, exchange history — was scoped out intentionally. Those surfaces have their own complexity. This project was about one question: does the first five minutes earn trust, or spend it?

Good tools don't compromise privacy. They protect it.
